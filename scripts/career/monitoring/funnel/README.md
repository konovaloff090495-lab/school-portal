# Учёт профориентации: контроль 13 ноября 2026

Трафик Метрики 108789843 собирается отдельным скриптом root; этот модуль отвечает за первую сторону воронки. Продажи всех трёх партнёров находятся вне отчёта по прямому решению владельца. Измеряются только заявки, доставка/ошибка CRM и конверсии. Продажи, оплаты, выручка и статусы сделок не запрашиваются. Доставка не является продажей.

## Снимки и отчёт

Команды только читают SQLite на VPS и возвращают агрегаты, без ключа шифрования и расшифровки контактов:

```sh
python3 scripts/career/monitoring/funnel/measurement.py snapshot --date1 2026-11-06 --date2 2026-11-12 --output /path/to/funnel-2026-11-13.json
python3 scripts/career/monitoring/funnel/measurement.py report --snapshot /path/to/funnel-2026-11-13.json --output /path/to/funnel-report
```

Время сервера/даты этапов приводятся к Москве. Для промежуточного снимка date2 ставить текущую дату, помечая её незавершённой. Не сравнивать неполный 6 ноября с полными сутками. Фактическое начало точного учёта — `tracking_meta.activated_at_utc`, а не полночь даты запуска.

`baseline-2026-11-06.json`: read-only снимок 06 ноября 13:42 МСК перед v2:0 сохранённых результатов и заявок в текущих таблицах,10 старых клиентских событий. В 13:30 их было 4, остальные появились позже; все старые события неразмечены QA/real. Это НЕ доказательство нулевых исторических лидов: три служебные отправки в CRM ранее проверены и удалены вместе с временными результатами. Они не включаются в боевые показатели, а неизвестные прежние показатели не заменяются нулями.

## Что считается

- `career_landing_view`: просмотр 69 точных публичных страниц, включая 9 старых статей через точечный bootstrap общей навигации.
- `career_cta_click`, `career_test_start`, `career_question_view` / `career_question_answered` с номером 1–24, `career_test_complete`, `career_gate_view`.
- `career_result_saved`: сервер сохранил результат, ровно один раз в транзакции, не на клиентский клик.
- `career_result_view`, `career_offer_view`, `career_offer_select`.
- `career_partner_request_saved`: сервер принял одну заявку выбранному партнёру.
- `career_crm_delivered` / rejected / uncertain / configuration_error: подтверждённое состояние адаптера. Таймаут не является ни успехом, ни продажей.
- `career_feedback_easy` / difficult: добровольный UX-пульс, один голос на journey, без свободного текста и нового гейта.

`funnel_counts` — устойчивые агрегаты; удаление контакта/результата и очистка 180-дневных данных их не уничтожают. В `funnel_events`30 дней только HMAC анонимного journey, время, событие, публичная посадочная, фиксированные cohort/offer/grade/step/elapsed. Нет контактов, ответов, результата, cookie или токена доступа. Связь с исходным journey хранится только внутри зашифрованных рабочих данных. В выгрузке нет и HMAC journey: только SQL-агрегаты.

## Знаменатели

Главная конверсия: отдельные journey, у которых есть сохранённая сервером заявка, среди journey с первым измеренным входом на одну из 69 публичных страниц в периоде. Даже если один человек выбрал трёх партнёров, числитель основной конверсии равен 1. Событий заявок может быть 3 — это отдельный показатель.

Для партнёра: число отдельных journey с заявкой и наблюдавшимся показом его предложения / journey, увидевшие это предложение. Повторные просмотры и три партнёра не суммируются в основной коэффициент. Нулевой знаменатель → `null` / «нет знаменателя», не 0% и не деление на 1. Серверные заявки без наблюдавшегося клиентского показа остаются в счётчиках, но не создают выдуманный CTR.

Journey — единица sessionStorage, а не человек, посетитель или визит Метрики. Новая вкладка, устройство, очищенное хранилище или переход по личной ссылке могут создать другое прохождение. Повторный тест в той же вкладке может оставить тот же journey. Когортная воронка точна только для наблюдаемого пути в этом пространстве идентификаторов. Связывать её с пользователем Метрики или объявлять точной межустройственной конверсией нельзя.

## Когорты и QA

Когорта рассчитывается сервером по захваченным первым UTM и hostname источника: organic / paid / campaign / referral / internal / direct / unknown / qa. Не хранится полный referrer URL, query или raw search term в measurement. В browser tracking сохраняются только hostname, безопасные source/medium, QA-маркер и признаки наличия рекламного click ID; сами click ID не нужны этому трекеру. Исходная атрибуция CRM хранится отдельно и не меняется.

Явные QA-маркеры — значения UTM с префиксом qa_ или qa-. Дополнительно сервер может знать точный список служебных email через `CAREER_QA_EMAILS` (запятая) и имён `CAREER_QA_NAMES` (вертикальная черта); значения только в защищённом env, без выгрузки в отчёт. Общие слова test/тест не служат основанием исключать настоящего пользователя. При распознавании известного служебного контакта события его journey в пределах 30 дней переносятся из боевой когорты вqa, не удаляются. Это предотвращает примесь ранних тестовых шагов к organic. Для новых проверок всё равно использовать qa_* с самого входа.

Старый `event_counts` оставлен для совместимости. В отчёте его неразмеченный остаток вычисляется после вычитания новых v2-клиентских агрегатов, чтобы не объявлять все новые события «старыми неизвестными».

## Интерпретация CJM

Номер шага не содержит ответа. Просмотр шага без зарегистрированного ответа — сигнал для проверки, а не доказательство сложности: человек мог отложить опрос, закрыть вкладку, потерять сеть или заблокировать событие. Повторные тесты одного journey могут смешивать шаги нескольких попыток. Elapsed — диапазон времени от старта, включая паузы и перезагрузку; это не активное время решения. Отчёт сохраняет диапазоны, не выдумывает среднее или медиану из бакетов.

UX-оценка добровольная и подвержена самоотбору. При маломN формулировка «отзывов недостаточно», а не «CJM доказанно удобен». Решения 13 ноября опираются на этапные потери, ошибки доставки, время и добровольную оценку вместе; при наличии проблемы — просмотр соответствующего сценария и короткие интервью.
