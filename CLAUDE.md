## Architecture

**School catalog portal** for Russia (`pro-schools.ru`). Next.js 16 App Router, React 19, Tailwind v4, TypeScript 5. No database — all data lives in `/src/data/` as large TS/JSON files (~50MB total). Every dynamic route is statically pre-rendered via `generateStaticParams()`.

### Data layer

| File | Size | Contents |
|------|------|----------|
| `src/data/schools.ts` | ~6MB | 10k+ schools with typed structs |
| `src/data/gdz-books/` | ~6MB+ | GDZ: `index.json` (метаданные книг) + JSON на книгу, читаются с диска лениво (`src/data/gdz.ts`); правки через `scripts/gdz_lib.py` |
| `src/data/textbook-articles.json` | ~37MB | Textbook content |
| `src/data/blog.ts` | — | Blog posts |
| `src/data/ege-oge.ts` | — | Exam resource links |
| `src/data/reviews.ts` | — | School reviews |

TypeScript build errors are suppressed (`ignoreBuildErrors: true`) to avoid timeouts on giant data files. Always run `npx tsc --noEmit` locally before pushing.

### Routing

```
/shkoly/[region]/                        # schools by region
/shkoly/[region]/[type]/                 # filtered by type
/shkoly/[region]/profilnye/[profile]/    # profile schools (IT, medical…)
/gdz/[klass]/[subject]/[book]/[number]/  # homework solutions
/uchebnik/[subject]/[klass]/[topic]/     # textbook hierarchy
/blog/[slug]/                            # blog posts
/test/, /test/extended/                  # career aptitude tests
/lk/                                     # user profile (localStorage)
/poisk/                                  # client-side full-text search
/admin/otzyvy                            # review moderation (secret param)
```

### Client vs server components

Nearly all pages are server components (direct data imports, no `use client`). Only six client components exist: `CatalogClient`, `SearchPageInner`, `CareerTest`, `ExtendedTest`, `ApproveButton`, `LeadForm`. Prefer server components; add `use client` only when interactivity requires it.

### SEO patterns

Every page exports `Metadata` built via helpers in `src/lib/utils.ts` (`buildTitle`, `buildDescription`, `buildKeywords`). JSON-LD is generated by `src/lib/schema.tsx`. `trailingSlash: true` is set globally — keep URLs consistent.

### Key integrations

- **Leads**: `/api/leads/submit` → Telegram + CRM Синергии (GraphQL `sendLead`, `src/lib/synergy.ts`) + Formspree (если задан)
- **Reviews**: GitHub API (fine-grained PAT) — moderation via `/admin/otzyvy`
- **Analytics**: Yandex Metrika (no GA)
- **Ads**: Yandex РСЯ — CSP in `next.config.ts` allows their iframes
- **Deployment**: VPS Бегет 45.80.70.209 через PM2 + Nginx (порт 3001). НЕ Vercel.

### Scripts

`/scripts/` contains Node/Python scripts for offline data enrichment and batch content generation (uses `@anthropic-ai/sdk`). These are run locally, not deployed.

## Лид-формы — ОБЯЗАТЕЛЬНОЕ ПРАВИЛО

**Любая форма, собирающая имя/телефон (существующая или новая — на любой новой странице,
поп-апе, баннере, квизе), отправляет заявку ТОЛЬКО через `submitLead()` из `src/lib/submitLead.ts`.**
Тогда заявка автоматически уходит в Telegram и в CRM Синергии (GraphQL `sendLead`,
landCode `mo_tilda_online_school`, `utm_source=gerasimov_lav`, школа/город/комментарий
в `latestComment`, UTM/страница/реферер/ClientID Метрики в `customAttributes`).

- Каждой форме — свой уникальный `source` (это `formTitle` в CRM и подпись в Telegram).
- Две отдельные галочки согласий: ПДн (обязательная, `/politika-konfidentsialnosti/`)
  и маркетинг (`/soglasie-marketing/`, по умолчанию выключена); значения передаются как `pd_agreed` / `marketing_agreed`.
- Маска/валидация телефона — `formatPhone` / `validatePhone` из `src/lib/phone.ts`.
- B2B-формы (рекламодатели, «разместить школу») — тоже через `submitLead()`, но с `crm: false`.
- Прямой `fetch('/api/leads/submit')`, Formspree/Tilda/Bitrix в компонентах — запрещены.
- Гард `scripts/check-lead-forms.sh` (`npm run lint:leads`) запускается в `deploy.sh` перед сборкой
  и **останавливает деплой**, если файл с `type="tel"` не импортирует `submitLead`.
- Тест интеграции без dev-сервера: `SYNERGY_GRAPHQL_URL=https://api.school.syndev.ru/graphql npx tsx <скрипт с import './src/lib/synergy'>` из корня проекта.

## Deploy (VPS Бегет)

**После любых правок — сразу деплоить без подтверждения юзера.** В ответе одна строка: «задеплоил → https://pro-schools.ru/».

**Прод** — VPS 45.80.70.209, домен pro-schools.ru, PM2 `school-portal` на порту 3001, Nginx reverse-proxy с SSL (Certbot).

### Стандартный деплой

```bash
# 1. Коммит и пуш
git add -A && git commit -m "..." && git push origin main

# 2. Деплой на VPS
./deploy.sh
```

**Стратегия: сборка ЛОКАЛЬНО на Mac + rsync `.next` на VPS.** Turbopack на VPS
падает из-за нехватки RAM, поэтому билд гоняем локально (4 ГБ heap) и заливаем
готовый `.next` на прод. `deploy.sh` делает автоматически:

1. SSH → `git pull origin main` на VPS (ключ `/root/.ssh/github_school_portal`, до 5 ретраев)
2. Локальная сборка: `NODE_OPTIONS=--max-old-space-size=4096 npm run build`
3. Читает локальный `.next/BUILD_ID`
4. Сборка (без cache/dev) упаковывается в один tar.gz; rsync по отдельному SSH-соединению передаёт архив, SHA256 проверяется до распаковки в `.next-incoming/`. Статика `public/` передаётся отдельно (до 5 ретраев,
   с реальной проверкой кода возврата — обрыв SSH во время rsync ловится)
5. **Гейт безопасности по BUILD_ID**: читает `.next-incoming/BUILD_ID` на VPS (до 5 ретраев) и
   сверяет с локальным. Не совпал → `.next` долит не полностью → выход БЕЗ рестарта,
   прод остаётся на прежнем билде
6. Добавляет пути VPS в client-reference manifests; запускает проверку холодного рендера на 127.0.0.1:3197. Затем переключает `.next-incoming` → `.next`, сохраняет `.next-previous` и откатывается при провале health check.
7. Проверяет HTTP 200 и best-effort пингует sitemap (GSC) + IndexNow

Все SSH/rsync-шаги обёрнуты в ретраи, т.к. этот VPS часто рвёт соединение на
banner exchange.

### SSH

```bash
ssh -i ~/.ssh/id_ed25519 root@45.80.70.209
```

SSH часто обрывается (`kex_exchange_identification`). Всегда оборачивать в until-loop:

```bash
until ssh -i ~/.ssh/id_ed25519 -o ConnectTimeout=15 root@45.80.70.209 'echo ok' 2>/dev/null; do sleep 15; done
```

### RAM (важно!)

VPS 3.8 GB делится с seocheckup (PM2 `seocheckup`).
- Runtime на VPS: `NODE_OPTIONS=--max-old-space-size=1536`, `max_memory_restart: 1800M`
- Сборка на VPS **не идёт** — Turbopack там OOM-ится. Билд гоняется локально на Mac
  с `NODE_OPTIONS=--max-old-space-size=4096`, на VPS уезжает только готовый `.next`

### Что НЕ делать

- НЕ деплоить через `vercel --prod` — прод только VPS
- НЕ собирать на VPS (`npm run build` по SSH) — Turbopack там OOM-ится; билд только локально
- НЕ перезапускать PM2 в обход гейта BUILD_ID, если rsync `.next` мог оборваться —
  поднимете неполный билд
- НЕ чистить `.next` пока идёт локальная сборка — сломает текущий билд


### Исправление индексации и деплоя 25.09.2026

- GitHub Actions `.github/workflows/deploy.yml` больше НЕ деплоит по push; workflow отключён в GitHub. Старый сценарий запускал `npm ci` и `pkill` на боевом VPS параллельно локальному deploy.sh, вызывая 502. Не включать его обратно.
- Локальный `.deploy-lock` не даёт двум deploy.sh менять сборку одновременно. При аварийном завершении сначала проверить процессы, только потом убирать устаревший lock.
- Сборка передаётся в `.next-incoming`, а не поверх работающего `.next`. Холодный рендер проверяет ГДЗ, каталог олимпиад и legacy-редирект. Ошибка останавливает выкладку до переключения.
- Нельзя восстанавливать удалённые ГДЗ-заглушки ради нулевого счётчика 404. Старые номера Перышкина 63/223 и др. не содержали настоящих решений; в актуальных внутренних ссылках и sitemap их нет.
- Старые `/shkoly/<school-slug>/` перенаправляются по таблице 206 точных существующих карточек из GSC (scripts/seo/legacy-school-paths.json), через next.config.ts до рендера. Runtime permanentRedirect в ISR-маршруте здесь не использовать: повторный ответ Next 16.2.4 дублировал Location. Валидные города и неизвестные школы не затрагиваются. В учебнике числовые классы 1–11 нормализуются в `N-klass`.

- deploy.sh требует локальный zstd и tar с --no-xattrs (macOS), на VPS GNU tar --zstd. Архив проверяется SHA256; long-window zstd сокращает текущую сборку с 627 до 64 МиБ. SSH использует отдельный multiplex-сокет внутри .deploy-lock только на время этого деплоя (закрывается при выходе). Так между шагами не повторяется нестабильный banner exchange; общий пользовательский сокет не используется.

- Если SSH обрывается на banner exchange: не делать частых проб. Каждая новая попытка продлевает блокировку VPS; выдержать минимум 150 секунд без SSH, затем одна сессия ControlMaster на всю выкладку. См. feedback_vps_ssh_controlmaster.md в общей памяти.

- Если уже есть проверенный живой SSH master того же root@45.80.70.209, можно передать DEPLOY_SHARED_SSH_SOCKET=путь ./deploy.sh --no-build. Чужой master при выходе НЕ закрывается и его сокет НЕ удаляется.

## Сквозная навигация — обязательное правило (20.10.2026)

Единые шапка и подвал утверждены Дмитрием для ВСЕХ страниц и будущих макетов.
Канонический источник: `src/site-navigation/chrome.json`; общие стили/поведение:
`public/site-navigation/`. Интеграция и правила: `docs/navigation/README.md`.
React получает Header/Footer из root layout. Статические курсы и программирование
читают тот же JSON. Новые генераторы и макеты в любых сессиях используют эти же
фрагменты и ресурсы, а не собственную копию и не старые courses/design/chrome/*.
Перед выкладкой запускать `python3 scripts/check-navigation.py`; новый рендерер
добавлять в эту проверку. Город называется «Ваш город», поиск отделён от меню.

### Добавление разделов в навигацию

Обязательный регламент: `docs/navigation/adding-sections.md`, реестр:
`docs/navigation/sections-policy.json`. В верхнем уровне сейчас 7 разделов;
подразделы добавлять в существующие группы, не дописывать восьмой пункт автоматически.
Названия и порядок desktop/mobile совпадают; основные разделы доступны в подвале.
Одно изменение — во всех рендерерах и макетах. Проверка без сборки:
`python3 scripts/check-navigation-policy.py`; она запускается в облачной сборке и деплое.

### Сборка без нагрузки на Mac

По решению Дмитрия 20.10.2026 тяжёлую сборку выполнять в существующем ручном
GitHub Actions `build-release.yml`, затем проверять SHA256, BUILD_ID и SOURCE_COMMIT.
Перед выкладкой сравнивать compiled src/config/package от SOURCE_COMMIT до HEAD.
Публиковать проверенный артефакт через `DEPLOY_BUILD_ID_FILE=... ./deploy.sh --no-build`
и `DEPLOY_PUBLIC_MODE=committed`, если незавершённые public-правки других сессий
не входят в релиз. На боевом VPS сборку не запускать. GitHub workflow сам не деплоит.
